| Area                               | What is wrong                                                                                                                                          | What needs fixing                                                                                                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1. Message handling**            | Messages submitted on V1 can be accepted without being recorded as delivered. The no-route behavior also differs from the stated retry policy.         | Correct local delivery and define consistent retry/drop rules across firmware, paper, and tests.                                                                                    |
| **2. Complete records**            | The dashboard retains only the latest **20 incidents**. Its counts and exports can therefore look like complete results when they are not.             | Preserve complete experimental logs and clearly distinguish recent records from cumulative totals.                                                                                  |
| **3. Timing**                      | Arrival gaps and hub uptime can be mistaken for delivery latency. Actual latency is unavailable when the clocks are unsuitable.                        | Establish a reliable time reference and use sender/receiver logs to explain delays. **The reported 13 seconds still needs investigation.**                                          |
| **4. Live connection reliability** | The dashboard sometimes loses its live feed but continues showing previous records. Requests can also remain pending without clear recovery.           | Investigate request failures, add timeout/reconnection behavior, and clearly mark live, stale, empty, and unavailable data.                                                         |
| **5. Access controls**             | The community passcode is exposed, and administrative pages/data are accessible without authentication on every node.                                  | Remove exposed credentials, retain server-side validation, and protect administrative access on V1.                                                                                 |
| **6. Admin dashboard usability**   | Important emergency details compete with technical columns. Small text, incomplete references, and ambiguous SOS counts make interpretation difficult. | Prioritize urgency, location, message, complete reference, and receipt information. Put technical details in a secondary view and clarify what each count means.                    |
| **7. Resident portal usability**   | Hard-coded node information, technical wording, automatic SOS selection, unclear submission states, and input handling can confuse users.              | Show accurate node information, simplify reporting, preserve entered text, clarify queueing versus delivery, and prevent misleading confirmations or accidental repeat submissions. |
| **8. Research-data validity**      | The shield battery is not yet measured through a verified sensing path. Current ACK/NOACK labels do not establish actual receiver-side delivery.       | Verify and calibrate battery sensing, reconcile sender/receiver records, and exclude uncertain outcomes from training labels.                                                       |
